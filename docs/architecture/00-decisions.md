# 00 — Ambiguities, Decisions and Tradeoffs

The spec is thorough but leaves a number of engineering choices open. Each row below records the ambiguity, the decision, and the cost of that decision. These are proposals — flag any you disagree with before Phase 1.

| #   | Ambiguity in spec                                                      | Decision                                                                                                                                                                                                                                                                                                                                                                                                             | Tradeoff / why                                                                                                                                                                                                                                              |

The worker also supports `--once` (run all due work then exit).                                                                                                                                                                                                                                        | Shares modules, DI, DB layer and tests. `--once` mode is what makes the worker portable to cron-style free hosts (GitHub Actions, Windows Task Scheduler, any cron) when a long-lived free process is not available.                                        |

## Items the spec asks for that are intentionally deferred (not dropped)

- HTML career-page adapter (cheerio first, Playwright only if needed) — after ATS/RSS/API adapters prove the pipeline. Only runs with a `robots.txt` check, a per-domain rate limit and a conservative `User-Agent` that identifies the bot.
- Google OAuth login — after email auth works.
- `LocalModelAdapter` implementation — interface only in MVP.
- Web push notifications — Telegram covers instant alerts; the dashboard shows an in-app inbox.
- OCR for scanned resumes.

## Decisions taken during implementation

| D25 | (Phase 1) NestJS 12 is ESM-only (`"type": "module"`)                              | **Pin NestJS to the 11.x line (CommonJS).**                                                           | Avoids an ESM migration of the API + Jest/ts-jest/decorator-metadata friction. NestJS 11 is mature and fully supported; upgrade to 12 is a self-contained later task.  |
| D26 | (Phase 1) `typescript@latest` resolves to 7.x (native Go compiler)                | **Pin TypeScript to `~5.9`.**                                                                         | ts-jest, Nest CLI and ESLint type-checking are validated against 5.x; 7.x can be adopted once the toolchain supports it.                                               |
| D27 | (Phase 1) Next.js 16 renamed `middleware.ts` → `proxy.ts`                         | Use `proxy.ts`; Supabase session refresh + optimistic auth redirects live in `lib/supabase/proxy.ts`. | Follows the framework; docs 04 references to "middleware" mean `proxy.ts`.                                                                                             |
| D28 | (Phase 1) Package build outputs                                                   | Packages compile to `dist/` (CJS) and are consumed via `main`/`types`; `pnpm build` is topological.   | Simple and works for Nest (CJS) and Next (bundles). Requires `pnpm -r --filter './packages/*' build` before running the API from source in dev — documented in README. |
| D29 | (Phase 1) shadcn CLI now generates Base UI-based components with the `cn` package | Accepted as generated.                                                                                | Newer shadcn defaults; Gemini should keep using the CLI for new components rather than hand-porting Radix versions.                                                    |

| D30 | (Phase 2) `jose` v6 is ESM-only | Pin `jose@^5` (dual CJS/ESM, same API). | Same reasoning as D25; revisit together with an ESM migration. |
| D31 | (Phase 2) `unpdf` lazily `import()`s pdf.js, which Jest's VM blocks | API e2e runs with `NODE_OPTIONS=--experimental-vm-modules` (`cross-env`). | Works in plain Node without flags; only the Jest sandbox needs it. |
| D32 | (Phase 2) Gemini `responseJsonSchema` rejects some JSON-Schema keywords | `sanitizeSchemaForGemini()` strips `maxItems` / `minItems` / `default` / `additionalProperties` / `$schema` (verified live). Zod still enforces the full schema on the response. | Constraints are enforced on our side anyway; the model just sees a slightly looser schema. |
| D33 | (Phase 2) Gemini Lite models reject `thinkingConfig` | `thinkingBudget` is an optional adapter setting, only sent when configured. | Thinking models (e.g. `gemini-3.6-flash`) need larger output budgets; default model stays `gemini-3.5-flash-lite` for structured extraction. |
| D34 | (Phase 2) Vendor SDKs vs REST | AI adapters call the REST APIs directly with `fetch` (no `@google/genai` / `@anthropic-ai/sdk`). | Fewer, lighter deps; trivially mockable; the interface is unchanged if an SDK is ever preferred. |
| D35 | (Phase 2) Deleting an auth user cascades DB rows but not Storage objects | `DELETE /resumes/:id` removes the object; the Phase 12 "delete my data" flow must delete storage objects before the auth user. | Documented so it is not forgotten; e2e cleanup already does it. |
| D36 | (Phase 4) ISP uses NAT64; `64:ff9b::` answers looked "internal" to the SSRF guard | Decode the embedded IPv4 from `64:ff9b::/96` and judge that address. | Keeps the guard strict for real private ranges while working on IPv6-only/NAT64 networks. |
| D37 | (Phase 4) Per-row DB round-trips made large boards time out (~1 job/s over a ~100 ms pooler) | Batched dedupe (50 per transaction): one lookup per key type per batch, bulk inserts. | ~7 jobs/s; per-batch transaction keeps failures atomic. |
| D38 | (Phase 4) Bytes per job dominated scan time on a residential uplink (text + HTML + raw HTML ≈ 35 KB) | Store plain text only (`description_html` stays null; sanitized HTML is regenerated on demand), strip description fields from `raw_payload`, default `SOURCE_SCAN_TIMEOUT_MS` = 10 min. | Detail page renders text with line breaks; a future `description_html` can be re-enabled if the host has bandwidth. |
| D39 | (Phase 4) Embedded Greenhouse boards put the job id in `?gh_jid=` | `gh_jid`/`ashby_jid` are identifiers, never stripped as tracking params. | Stripping them collapsed every job of such a board into one — caught by the live run. |
| D40 | (Phase 4) Level markers in titles ("Software Engineer 1/2/3", "II", "L2") | Kept in the dedupe key; only marketing noise and batch years are removed. | SE-1 and SE-3 are different jobs for a fresher; mild risk of two mappings for the same posting listed once with and once without a level. |
| D41 | (Phase 4) ATS slugs are global namespaces | Seed only boards whose postings' locations confirm the intended company; Lever `porter`/Ashby `navi` removed. | Company identity is part of source validation from now on (documented in docs/sources.md). |
| D42 | (Phase 5) Job boards are dominated by non-engineering roles (1,100 of 2,651) | A `NON_ENGINEERING` gate runs before role-family matching, with an override list so technical hybrids ("Sales Engineer", "Technical Account Manager") stay on the engineering side. Such jobs are stored and `FILTERED_OUT`, never deleted. | Preferences can widen later without re-scanning; the AI budget is never spent on a sales role. |
| D43 | (Phase 5) Level markers in titles ("Engineer 3", "L2", "II") are the most reliable seniority signal after parsed years | Treated as senior indicators; an internship still outranks every seniority word ("Product Management Intern" is a fresher job). | Caught by measuring against real data — the first version called "Software Engineer 3" fresher-eligible. |
| D44 | (Phase 5) Per-job transactions cost ~0.4 s over the Supabase pooler | Classification writes one `UPDATE … FROM (VALUES …)` plus one bulk event insert per batch, inside a single transaction. | 100× faster (0.33 → 39 jobs/s), which is what makes "re-classify everything after a preferences change" usable. |
| D45 | (Phase 5) Free-tier Gemini latency was measured at 60 s+ under load | `AI_REQUEST_TIMEOUT_MS` (default 20 s) plus a per-batch AI time budget; on timeout the deterministic verdict stands and the job is marked `aiUnavailable`. | A degraded provider slows nothing but the AI refinement; the pipeline keeps its throughput. |
| D46 | (Phase 5) e2e suites share one live Supabase project | The e2e Jest config runs with `maxWorkers: 1`. | Parallel workers were classifying each other's fixtures; serial runs are slower but honest. A second Supabase project per test run would be the alternative. |
| D47 | (Phase 6) Scam wording appears in honest postings that warn about scams | Patterns marked `honorNegation` are skipped when the same sentence contains a negation ("we **never** charge a registration fee"). | Caught by a fixture written specifically to break the detector; without it, careful employers would be flagged as frauds. |
| D48 | (Phase 6) Short brand names collide under edit distance (`zeta.tech` vs `okta.com` = 2) | Look-alike detection ignores labels under 5 characters and scales its tolerance with length (1 for short, 2 for ≥ 8). | Found on live data: Zeta was flagged as impersonating Okta. Fewer look-alikes are caught, but the flag is costly enough (−0.4) that a false positive is worse than a miss. |
| D49 | (Phase 6) Many career pages answer automated requests with 403/429 | A verified company + application link on its own domain/ATS + no scam flags stays **VALID** (confidence capped at 0.8) with the failed page check recorded as evidence. Anything weaker is NEEDS_REVIEW. | 39 of 120 live postings were bot-protected; forcing them all to manual review would make the queue useless. This is what docs 08 §3.3 already prescribed ("unless ATS evidence strong"). |
| D50 | (Phase 6) A NEEDS_REVIEW verdict was showing confidence 0.90 | Confidence is capped at 0.65 whenever the status is NEEDS_REVIEW. | "We could not confirm this" must never be displayed next to a near-certain number. |
| D51 | (Phase 7) A matching run held one pooled connection open across every AI call | Scores are flushed to the database every 50 jobs, and in any case every 60 s, instead of once at the end of the batch. | Found live: a 300-job run spent ~10 min in AI calls (including a Gemini 503 retry) and then died with `CONNECT_TIMEOUT` on the Supabase pooler, losing all 192 scores. Flushing also makes a run resumable — re-running skips jobs already scored at the current profile version. |
| D52 | (Phase 7) A senior role can out-score a fresher role on title, skills and location alone | When the experience component scores 0 (an EXPERIENCED posting under a `fresherOnly` profile), the overall score is capped at 45 — below the MEDIUM band — in both the deterministic scorer and after AI refinement. | Found on the live run: "Senior Backend Engineer (Python)" reached 62 (MEDIUM) and the unit test had frozen the same bug at 80 (HIGH). Experience is only 20 % of the weight, which is right for ranking similar jobs but wrong as a veto. The job is still scored and ranked, never hidden. |
| D53 | (Phase 7) docs 07 §1.4 routes a job with no AI refinement to the `AI_PENDING` **status**, but that status would take it out of `MATCHED` | The pending set is expressed as _a match row at the current profile version with `ai_provider IS NULL` and a score above the pre-filter_, drained by `MatchingService.refinePending()` in the worker's `refine` stage. The job keeps `MATCHED`. | docs 09 §6 requires the dashboard to keep showing these jobs, since their deterministic score is already stored — so `AI_PENDING` as a job status would have to be treated as "matched anyway" by every reader. A nullable column already carries the fact; a second status carrying the same fact is a state machine with two sources of truth. The `AI_PENDING` enum value is retained for validation, which has no equivalent column. |
| D54 | (Phase 8) `GET /dashboard/summary` fanned out 8 parallel queries and could stall | All fourteen counters are one statement of scalar subqueries; the endpoint now issues 3 queries (counters + two card lists). `statement_timeout` (60 s) and `idle_in_transaction_session_timeout` (30 s) were added to the connection. | Round trips dominate cost on a shared pooler, so one statement is faster regardless (~1.4 s → one query). The stall was found to be a test-harness limit — under Jest's `--experimental-vm-modules`, postgres.js stops draining its queue above the pool's `max` (4 concurrent fine, 6 hang), while plain Node handles 12 — but fanning out more queries than the pool holds is a bad habit in any case. The timeouts are the real production safeguard: abandoned backends were observed `active` for 13 minutes, and a pooler queues new clients when its slots are full. |
| D55 | (Phase 8) A JS `Date` interpolated into a raw `sql` template throws `ERR_INVALID_ARG_TYPE` | Timestamps in raw SQL are passed as `value.toISOString()` with an explicit `::timestamptz` cast; typed helpers (`gte(col, date)`) still take a `Date`. | Drizzle only attaches a column encoder when the value goes through a typed operator; inside a raw template it hands the `Date` straight to postgres.js, which expects a string. It failed three separate queries in this phase, always at runtime, never at compile time — hence the rule rather than a one-off fix. |
| D56 | (Phase 9) Telegram rejects an inline keyboard containing a non-public URL, dropping the whole message | Button URLs are checked with `isPublicUrl`; a `localhost` dashboard loses the "View" button, never the alert. | Found on the first live send: every message failed with `Bad Request: … is invalid: Wrong HTTP URL` because `APP_BASE_URL` is `http://localhost:3000` in development. Losing one button in dev is acceptable; losing the alert — including its APPLY link — is not. |
| D57 | (Phase 9) The classification category gate is the union of every user's monitored categories, so a test cannot make a category unmonitored | The integration test derives an unmonitored category at runtime and skips that assertion if every engineering category is watched. | The test passed only while no real account existed; creating the owner's account made a `DATA` job legitimately CLASSIFIED and the test failed. The behaviour was right and the assumption was wrong — a test must not depend on the absence of real data. |
| D58 | (Phase 10) The daily AI budget cannot see a per-**minute** limit, so a batch burns Gemini's free-tier 15 rpm in seconds | `AIService` paces calls with `AI_MIN_REQUEST_GAP_MS` (default 4.5 s ≈ 13/min) and, on a 429, parses the provider's "retry in Ns" hint into a cooldown that later calls wait out. | Found by running the worker unattended: every AI call after the first fifteen failed 429 within one tick, and the retries spent more quota. Pacing costs wall-clock time on a background worker, which is the cheapest resource here. A paid key can set the gap to 0. |
| D59 | (Phase 10) A posting stating "at least 2 years" was labelled ENTRY_LEVEL and **fresher-eligible** | A parsed minimum of 2 years is never fresher-eligible: with no fresher wording it is EXPERIENCED, and with fresher wording it is a contradiction and goes to the AI as UNKNOWN. The old `min === 2 → ENTRY_LEVEL` fallback is gone. | Spotted in a real Telegram alert reading "at least 2 years · Fresher ✓" — the evidence list even recorded the years as `NEGATIVE` while the verdict said fresher. 28 jobs were affected and all 28 reclassified to FILTERED_OUT. A contradiction like this costs the user an application and the product its credibility, which is exactly what the fresher gate exists to prevent. |
| D61 | (Phase 10) Adzuna authenticates with `app_id`/`app_key` in the **query string**, and our errors and redirect chains are persisted | `HttpClient` redacts credential-bearing query parameters (`redactUrl`) everywhere a URL reaches an error message, a redirect chain or a log. | Error text is written to `scan_runs.error_message` and `job_sources.last_error`, so one failed Adzuna scan would have stored a live API key in the database. Redacting centrally protects every adapter, including ones not written yet. |
| D62 | (Phase 10) The job list was silently filtered to India whenever the user's preferences contained "India" | The list is scoped to the user's own `preferences.locations` (remote jobs and postings with no stated location always kept), and `anywhere=true` lifts it. Documented in `JobsQuery`. | The behaviour is right — 54 % of listable jobs are ones this user cannot take — but it was undocumented, hard-coded to one country, and impossible to turn off. Making it explicit keeps the benefit without the API quietly returning something other than what was asked for. |
| D63 | (Phase 10) One Adzuna scan could spend 20 of the 250 requests the free tier allows per **day** | `maxPages` (default 2) bounds pagination, and the scan interval is 6 h. Seven queries × 4 scans × 2 pages = 56 requests/day. | `MAX_ITEMS_PER_SCAN` is 1 000 and a broad India search matches 28 000+ postings, so every scan would have paginated to the cap. The quota is shared across all queries, so the whole integration would have died within hours. |
| D64 | (Phase 10) `worker --once --sources=<id>` always failed with "malformed array literal" | The ids are bound one parameter each (`id in (...)`) instead of interpolating the JS array into `any(...::uuid[])`. | A documented operational flag that had never worked: drizzle passes the array as a single parameter, which Postgres reads as a bare string. |
| D65 | (Phase 10) Adzuna answered HTTP 200 with an HTML page, and the adapter died on `JSON.parse` | The adapter asks for `Accept: application/json`, and a non-JSON body now fails with a message naming the source and status. | `HttpClient` defaults to `Accept: text/html,application/json;q=0.9` because it mostly probes job pages — Adzuna content-negotiates on that and returns marketing HTML. The default is right for probing and wrong for an API, so the adapter states its own preference. |
| D66 | (Phase 10) The API exited mid-request with `read ECONNRESET` — an unhandled rejection from a pooler TLS reset that nothing was awaiting | `installProcessGuards()` (`apps/api/src/common/process-guards.ts`) handles `unhandledRejection` and `uncaughtException`: a known transient socket failure is logged and the process continues; anything else is logged `fatal` and exits. Wired into both `main.ts` and `worker.ts`. | The Supabase pooler drops idle TLS connections, and the error surfaces from `TLSWrap.onStreamRead` outside any promise chain — Node's default is to kill the process. A long-running API dying for a reason unrelated to the work it was doing is the opposite of "never lose a job because a scan failed". Swallowing _everything_ would hide real bugs, so the allowlist is explicit and short. |
| D67 | (Phase 10) A hard "must be in India" gate in classification dropped every job with an unstated location — including remote ones | `isIndiaLocation` stays as written and tested; the _gate_ now accepts a job that is in India **or** remote **or** has no stated country. | Measured on live data before changing it: the hard gate kept 666 jobs and filtered 2 711, of which 832 were remote and 528 simply had no country field — 38 of them fresher-eligible. The predicate was right and its use was wrong; a location filter must not turn "unknown" into "no". User-facing location narrowing belongs in the list query (D62), which the user can lift, not in a pipeline stage that is hard to undo. |
| D68 | (Phase 10) `ai-budget.e2e-spec.ts` hard-coded a 500-call budget against the **live** `ai_calls` table, so a busy worker day failed the suite | Each test sizes its `DbBudget` relative to today's real usage (`roomFor(n)`), read once in `beforeAll`. | Same family as D57: a test must not depend on the absence of real data. The budget behaviour under test is "does it stop at the cap", which is a statement about the _margin_, not about the number 500. |
| D69 | (Phase 10) An authenticated request 500'd and the only log line was `Failed query: select … from "users"` — no reason | The catch-all exception filter walks and logs the `cause` chain (up to four levels), tagging each with its driver `code`. | Drizzle's `DrizzleQueryError` puts the SQL in its message and the actual failure (pooler timeout, socket reset, constraint) in `cause`, so logging `err.stack` alone discards the diagnosis. The failure was intermittent and cleared on restart — the instrumentation is what will identify it if it returns, rather than another guess. |
| D70 | (Phase 10) Marking a job "Applied" saved server-side but the detail page kept showing the old status | `TrackerActions` calls `router.refresh()` after every mutation, and "Not Tracking" now actually deletes the tracker row. | The job detail page is a **server component**: `job` is a prop, not a React Query entry, so `invalidateQueries` cannot touch it. Verified live — the write landed (the job appeared under Applied on the tracker board) while the control it was operated from showed no change. A control that silently lies about whether it worked is worse than one that errors. |
