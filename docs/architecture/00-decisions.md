# 00 — Ambiguities, Decisions and Tradeoffs

The spec is thorough but leaves a number of engineering choices open. Each row below records the ambiguity, the decision, and the cost of that decision. These are proposals — flag any you disagree with before Phase 1.

| #   | Ambiguity in spec                                                      | Decision                                                                                                                                                                                                                                                                                                                                                                                                             | Tradeoff / why                                                                                                                                                                                                                                              |
| --- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | Monorepo tooling not specified                                         | **pnpm workspaces**, no Turborepo/Nx initially. `apps/web`, `apps/api`, `packages/*`.                                                                                                                                                                                                                                                                                                                                | Fewer moving parts; Turborepo can be added later purely for caching without restructuring.                                                                                                                                                                  |
| D2  | "Background job monitoring agent" — separate service or inside NestJS? | **One NestJS codebase, two entrypoints**: `main.ts` (HTTP API) and `worker.ts` (scheduler + Telegram poller). The worker also supports `--once` (run all due work then exit).                                                                                                                                                                                                                                        | Shares modules, DI, DB layer and tests. `--once` mode is what makes the worker portable to cron-style free hosts (GitHub Actions, Windows Task Scheduler, any cron) when a long-lived free process is not available.                                        |
| D3  | Queue/scheduler technology                                             | **Postgres-backed scheduler** (`job_sources.next_scan_at` + `SELECT … FOR UPDATE SKIP LOCKED`). No Redis, no BullMQ.                                                                                                                                                                                                                                                                                                 | Zero extra infra, survives restarts, fits free tiers. Loses horizontal worker scaling — irrelevant for a personal single-worker system. The `SchedulerPort` interface is abstracted so BullMQ could be swapped in later.                                    |
| D4  | ORM / DB access                                                        | **Drizzle ORM + `postgres` driver**, SQL migrations checked into git (`drizzle-kit`). Supabase JS client used only for Auth (JWT verification) and Storage.                                                                                                                                                                                                                                                          | Drizzle is thin, type-safe and works with RLS/Postgres features. Prisma is heavier and its engine binary has caused problems on small free hosts.                                                                                                           |
| D5  | Does the frontend talk to Supabase directly?                           | **No browser-to-Postgres data access.** Browser uses Supabase Auth only; all data flows through the NestJS API with a bearer JWT. RLS is still enabled as defense-in-depth.                                                                                                                                                                                                                                          | One API surface to secure and test; slightly more code than direct Supabase queries.                                                                                                                                                                        |
| D6  | Single-user vs multi-user                                              | **Schema is multi-user (every user-owned row has `user_id`)**, but sign-up is gated by `ALLOWED_SIGNUP_EMAILS`.                                                                                                                                                                                                                                                                                                      | Personal use today, no rewrite if it ever becomes multi-user. Job/company/source tables are shared (global); matches, notifications, saved jobs, applications are per-user.                                                                                 |
| D7  | Which job sources to start with                                        | **MVP sources = public ATS job-board APIs** (Greenhouse, Lever, Ashby, SmartRecruiters, Workable) configured with a list of company slugs, plus **RSS/JSON feeds** (e.g. Remotive API, WeWorkRemotely RSS) and **Adzuna** (free API key). The HTML career-page adapter comes later and only runs when `robots.txt` permits. LinkedIn / Naukri / Indeed / Glassdoor are **explicitly out of scope** (ToS + anti-bot). | ATS APIs are public, JSON, stable, and are exactly what companies' own career pages read from — so we get "company career page" coverage without scraping. Coverage depends on maintaining a company list (seeded in Phase 4, editable from the dashboard). |
| D8  | Default AI provider                                                    | **Gemini (free tier) as default provider**, Claude adapter implemented alongside, `LocalModelAdapter` (Ollama / any OpenAI-compatible endpoint) as a stub with the interface fixed. Selection via `AI_PROVIDER` env.                                                                                                                                                                                                 | Gemini free tier covers a personal-scale workload; Claude quality is higher but paid. Every prompt has a Zod output schema and a deterministic fallback path when AI is unavailable.                                                                        |
| D9  | AI budget control                                                      | Hard **per-day call budget** (`AI_DAILY_CALL_BUDGET`), content-hash caching (`ai_calls` table), and AI only runs after deterministic filters pass.                                                                                                                                                                                                                                                                   | Keeps us inside free quotas; ambiguous jobs may wait until the next day if the budget is exhausted — they are queued (`AI_PENDING`), not dropped.                                                                                                           |
| D10 | Resume parsing                                                         | `unpdf` for PDF, `mammoth` for DOCX, text → AI structured extraction → **user confirms** on the onboarding screen. Original file stored in a **private** Supabase Storage bucket; max 5 MB; MIME + magic-byte validation.                                                                                                                                                                                            | No OCR for scanned/image PDFs in MVP (documented limitation, user is told to upload a text PDF).                                                                                                                                                            |
| D11 | Authentication method                                                  | **Supabase Auth**: email + password and magic link. Google OAuth optional later.                                                                                                                                                                                                                                                                                                                                     | Free, handles password reset/email verification; API verifies JWT via the project JWKS.                                                                                                                                                                     |
| D12 | Telegram integration style                                             | **Long polling from the worker** (`getUpdates`), not webhooks. Account linking via a one-time `/start <code>` deep link.                                                                                                                                                                                                                                                                                             | No public HTTPS URL needed for the worker → works from a laptop or any free host. Webhook mode is a config switch for later.                                                                                                                                |
| D13 | Hosting                                                                | Web: **Vercel Hobby**. API: **Render free web service** (sleeps when idle; acceptable for a dashboard). Worker: **any always-on free option**, in order of preference: Oracle Cloud Always Free VM → personal laptop/desktop (Task Scheduler) → GitHub Actions cron running `worker --once` every 30 min. DB/Auth/Storage: **Supabase free**.                                                                        | Free tiers change; the worker is a plain Node process + Dockerfile, so moving it is a config change, never a rewrite. Details and caveats in doc 14.                                                                                                        |
| D14 | Company legitimacy — how much can be verified for free?                | Evidence-based confidence: domain resolves + HTTPS reachable + application-URL domain relationship (same registrable domain, or a known ATS domain with matching company slug) + presence in ≥2 independent sources + user "trusted companies" list. **No paid company-data APIs.** Statuses are never "certain" — confidence 0–1 with an evidence list.                                                             | Cannot detect a sophisticated impersonation with a legitimately registered lookalike domain; unknown/new domains land in `NEEDS_REVIEW`.                                                                                                                    |
| D15 | Priority bands vs notification threshold                               | Instant Telegram alerts default to **score ≥ 75 (High / Very High)**; everything else goes to the daily digest. Threshold is a user preference.                                                                                                                                                                                                                                                                      | Avoids alert fatigue; user can lower it. Score never auto-rejects a job (spec principle 9).                                                                                                                                                                 |
| D16 | "Other engineering categories" (Mechanical, Civil, …)                  | Jobs carry a `category` (`SOFTWARE`, `IT_SUPPORT`, `NETWORK`, `CLOUD_DEVOPS`, `DATA`, `ELECTRICAL_ELECTRONICS`, `MECHANICAL`, `CIVIL`, `OTHER_ENGINEERING`, `NON_ENGINEERING`). Preferences select which categories are monitored; non-selected categories are still stored but hidden and never notified.                                                                                                           | Storing everything lets the user widen categories later without re-scanning.                                                                                                                                                                                |
| D17 | Timezone                                                               | All DB timestamps are UTC (`timestamptz`); user preference `timezone` defaults to `Asia/Kolkata`; digest default 08:00 local.                                                                                                                                                                                                                                                                                        | —                                                                                                                                                                                                                                                           |
| D18 | Testing frameworks                                                     | **Jest + Supertest** for `apps/api` and `packages/*` (per spec); **Vitest + Testing Library** for `apps/web` (Next.js ecosystem default); **Playwright** for browser E2E.                                                                                                                                                                                                                                            | Two unit runners across the monorepo is a small inconsistency; keeping Jest on the API matches the spec and NestJS tooling.                                                                                                                                 |
| D19 | Where Zod schemas and validation rules live                            | Zod DTO/domain schemas → `packages/types`. Deterministic validation rules (pure functions, no I/O) → `packages/validation`. AI adapters + prompts → `packages/ai`.                                                                                                                                                                                                                                                   | Pure packages are trivially unit-tested and reused by API + worker.                                                                                                                                                                                         |
| D20 | "A job closes after discovery"                                         | Every `VALID` job is **re-checked** on a decaying schedule (6h → 24h → 72h) until it is `EXPIRED` or 45 days old.                                                                                                                                                                                                                                                                                                    | Extra HTTP traffic (bounded, respectful of rate limits); dashboard never shows stale "active" jobs for long.                                                                                                                                                |
| D21 | Description similarity for duplicates                                  | **SimHash of normalized description** (64-bit, Hamming distance ≤ 6) + exact-key matching (company + normalized title + location, external ID, application URL). No vector DB, no AI for dedupe.                                                                                                                                                                                                                     | Cheap, deterministic, testable. Rare misses on heavily rewritten postings are acceptable.                                                                                                                                                                   |
| D22 | Dark/light mode, PWA                                                   | Both planned for Phase 11 (Gemini); PWA = manifest + installability + basic offline shell only.                                                                                                                                                                                                                                                                                                                      | —                                                                                                                                                                                                                                                           |
| D23 | Salary handling                                                        | Store `salary_min`, `salary_max`, `currency`, `salary_period`, `salary_text` (raw). Never invent a salary; unrealistic salary is a _suspicious indicator_, computed against a per-category band table in config.                                                                                                                                                                                                     | —                                                                                                                                                                                                                                                           |
| D24 | Resume versions                                                        | A user may upload several resumes; exactly one is `is_active`. Profile is derived from the active resume + user edits. Match scores are keyed by `profile_version` so re-uploading a resume triggers re-matching only for open jobs.                                                                                                                                                                                 | —                                                                                                                                                                                                                                                           |

## Items the spec asks for that are intentionally deferred (not dropped)

- HTML career-page adapter (cheerio first, Playwright only if needed) — after ATS/RSS/API adapters prove the pipeline. Only runs with a `robots.txt` check, a per-domain rate limit and a conservative `User-Agent` that identifies the bot.
- Google OAuth login — after email auth works.
- `LocalModelAdapter` implementation — interface only in MVP.
- Web push notifications — Telegram covers instant alerts; the dashboard shows an in-app inbox.
- OCR for scanned resumes.

## Decisions taken during implementation

| #   | Context                                                                           | Decision                                                                                              | Tradeoff / why                                                                                                                                                         |
| --- | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D25 | (Phase 1) NestJS 12 is ESM-only (`"type": "module"`)                              | **Pin NestJS to the 11.x line (CommonJS).**                                                           | Avoids an ESM migration of the API + Jest/ts-jest/decorator-metadata friction. NestJS 11 is mature and fully supported; upgrade to 12 is a self-contained later task.  |
| D26 | (Phase 1) `typescript@latest` resolves to 7.x (native Go compiler)                | **Pin TypeScript to `~5.9`.**                                                                         | ts-jest, Nest CLI and ESLint type-checking are validated against 5.x; 7.x can be adopted once the toolchain supports it.                                               |
| D27 | (Phase 1) Next.js 16 renamed `middleware.ts` → `proxy.ts`                         | Use `proxy.ts`; Supabase session refresh + optimistic auth redirects live in `lib/supabase/proxy.ts`. | Follows the framework; docs 04 references to "middleware" mean `proxy.ts`.                                                                                             |
| D28 | (Phase 1) Package build outputs                                                   | Packages compile to `dist/` (CJS) and are consumed via `main`/`types`; `pnpm build` is topological.   | Simple and works for Nest (CJS) and Next (bundles). Requires `pnpm -r --filter './packages/*' build` before running the API from source in dev — documented in README. |
| D29 | (Phase 1) shadcn CLI now generates Base UI-based components with the `cn` package | Accepted as generated.                                                                                | Newer shadcn defaults; Gemini should keep using the CLI for new components rather than hand-porting Radix versions.                                                    |

| D30 | (Phase 2) `jose` v6 is ESM-only | Pin `jose@^5` (dual CJS/ESM, same API). | Same reasoning as D25; revisit together with an ESM migration. |
| D31 | (Phase 2) `unpdf` lazily `import()`s pdf.js, which Jest's VM blocks | API e2e runs with `NODE_OPTIONS=--experimental-vm-modules` (`cross-env`). | Works in plain Node without flags; only the Jest sandbox needs it. |
| D32 | (Phase 2) Gemini `responseJsonSchema` rejects some JSON-Schema keywords | `sanitizeSchemaForGemini()` strips `maxItems` / `minItems` / `default` / `additionalProperties` / `$schema` (verified live). Zod still enforces the full schema on the response. | Constraints are enforced on our side anyway; the model just sees a slightly looser schema. |
| D33 | (Phase 2) Gemini Lite models reject `thinkingConfig` | `thinkingBudget` is an optional adapter setting, only sent when configured. | Thinking models (e.g. `gemini-3.6-flash`) need larger output budgets; default model stays `gemini-3.5-flash-lite` for structured extraction. |
| D34 | (Phase 2) Vendor SDKs vs REST | AI adapters call the REST APIs directly with `fetch` (no `@google/genai` / `@anthropic-ai/sdk`). | Fewer, lighter deps; trivially mockable; the interface is unchanged if an SDK is ever preferred. |
| D35 | (Phase 2) Deleting an auth user cascades DB rows but not Storage objects | `DELETE /resumes/:id` removes the object; the Phase 12 "delete my data" flow must delete storage objects before the auth user. | Documented so it is not forgotten; e2e cleanup already does it. |
